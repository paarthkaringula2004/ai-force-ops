# Organization agent sharing

On an Admin's Agents card, **Not shared** is an ash-grey button. Click it to open the project-themed share dialog, select User, Manager and/or Employee, then click **Done**. A saved share displays **Shared** in green. No links or individual invitations are required. Selected roles include all current and future accounts; recipients find the agent under **Shared with you**.

Every active member of a selected role, including future members, receives the agent under **Shared with you**. Access is checked against the current role on every preview/chat request. The link itself does not grant access. Accounts belonging to excluded roles, disabled accounts, disabled/demoted owners and agents in the Bin cannot use the shared preview.

Sharing freezes the root agent and connected specialist workflows into a server-side clone. Recipients receive only the agent name/purpose, answers and charts; the workflow definition, editable instructions and credentials are not exposed. Saving sharing again refreshes the clone to the current draft version. External project evidence is read at execution time through the Admin's connected tools; personal profile and workplace requests remain scoped to the recipient. Usage is recorded for the recipient.

Shared previews cannot edit, delete, configure or publish the original, and cannot execute external writes or approve actions. Clearing all role checkboxes and saving removes the share. Role removal, revocation and version changes are also checked during execution before results are returned.

Implementation: `lib/agent-sharing.ts`, sharing API routes, `components/agent-sharing.tsx`, `app/agent-builder/[agentId]/shared/page.tsx`, shared execution handling in `lib/agent-studio-runtime.ts`, and migration `0051_agent_role_shares.sql`. Separate share IDs prevent collisions between agents with the same UUID under different owners.

Verification: `node tests/agent-sharing.mjs` covers role distribution, owner checks, frozen clones, metadata, secret stripping, account/owner disablement, role updates, deletion, revocation, rejected approvals and duplicate agent IDs. `node tests/agent-studio.mjs` verifies shared execution against Admin scan fixtures, recipient personal data/usage and blocked external writes. Database fixtures are rolled back and model calls are stubbed; no real roles were granted access during browser verification. ESLint and the production build pass.

Browser verification confirmed the project-coloured dialog, ash-grey button, preserved agent order and dismissal of Order saved after 20 seconds. Order saved no longer appears on initial load, and has additional spacing from the Agents heading. Security questions refresh the latest completed organization scan report from PostgreSQL on every turn when the shared workflow has a connected scan-report, Agent Assist or Chart Visualizer capability. Earlier chat history does not establish current findings. Security replies include a server-rendered evidence footer with scan ID, completion time and check time in UTC; a newer queued/running/failed job is distinguished from the completed report. Missing reports or timestamps are disclosed. Agent Assist and charts retain the same scan provenance.

This is an on-demand read of current stored evidence, not a newly executed scan. Built-in chat tools expose no authenticated or active scanner execution; server capability evidence marks these unavailable and tells agents not to offer them based on tool names or saved descriptions. Existing shared workflow snapshots inherit these runtime rules without granting edit or write access. Continuous scan scheduling remains independent of chat requests.

Service-health and database-monitoring answers refresh connected stored health records at execution time, including follow-up questions to the Database Activity Monitoring Agent. Evidence carries source names, observation timestamps, retrieval time, age and explicit recorded/live capability flags. These infrastructure readings do not establish database query/audit activity. A server-rendered footer states that no live endpoint check ran. The runtime instructs all existing and shared agents to describe last recorded statuses, avoid unverified monitoring-outage claims, treat ServiceNow/security connectors as optional rather than database-monitoring prerequisites, and avoid offering unsupported live checks. Availability percentages require a numeric measurement, positive sample count, period and method; unsubstantiated values are withheld. Sample availability is not guaranteed uptime or an SLA.
